# Windows 0.18.4 退出修复

Windows 0.18.2 的音频线程发布状态时，会同步询问 Tauri 窗口是否可见。退出回调此前在窗口线程等待音频线程结束；若窗口询问已排队，就会互相等待，表现为点击退出后卡死。快速开关音频时，退出回调还可能等待一个正在回收旧线程的锁。

## 修改

- 退出先停止监测、取消音频启动/恢复；在后台等待采集线程自行释放 WASAPI/COM 或 Core Audio 对象，窗口事件循环继续响应。
- 清理完成后统一通过 Tauri 正常退出。重复退出请求不会重复清理或跳过清理；异常驱动清理超过 3 秒时结束等待，避免永久卡住。这一路径不使用任务管理器、强杀进程或关闭安全设置。
- 退出开始后拒绝重新启动音频，不再发送新的音频窗口查询。
- 主窗口底部增加“退出软件”，托盘图标关闭时也可使用。窗口右上角关闭仍表示转入后台，与原有行为一致。
- 不删除设置、历史记录或角色素材，不更改音频权限及非商用许可。

## 回归方法

`cargo test --manifest-path src-tauri/Cargo.toml --locked` 包含音频线程等候窗口响应、开关回收锁与重复退出请求的并发回归。

`node scripts/test-native-exit.mjs` 在独立临时设置与空日志中启动真正的原生应用，验证七种情况：确定性窗口查询/退出竞争、关闭音频、隐藏托盘、开启音频、开关音频后退出、启动即退出、连续退出。主窗口按钮用原生 WebView 点击并经过正式命令处理器；其他退出用与托盘一致的 `AppHandle::exit(0)`。所有通过项必须以状态码 0 正常结束、无外部终止信号且音频线程在等待期限内释放。

确定性竞争用三个显式测试开关启用，并不打开真实音频。Windows 其他音频用例尝试真实 WASAPI；若云端没有音频设备，会在报告中如实记录 unavailable，而不称为真实音乐播放验收。Mac 可用 `--skip-audio` 跑不新增音频授权的退出回归。

确定性竞争先等待两个原生 WebView 应答，再开启夹具；冷启动时间单独记录，退出仍须在七秒内正常结束且资源释放成功。另有独立的启动即退出用例。失败报告保留隔离窗口、采集与退出探针，避免把冷启动延迟误报为退出卡死。

Windows CI 在测试通过后分别生成在线/离线安装器，核对打包前后二进制哈希，在临时目录安装离线版，并对安装后的同一二进制再次运行七项退出测试。证据为候选产物中的 `WINDOWS_EXIT_FIX_VALIDATION.json` 和 `SHA256SUMS.txt`。

云端 Windows 回归不代替用户实机复测；Windows 10、异机硬件、真实播放/设备切换、新标准用户、没有 WebView2 的干净系统与浏览器信誉提示仍需另测。旧 0.18.2 安装器不含本次修复，不能仅因仓库更新就视为已更新安装。
